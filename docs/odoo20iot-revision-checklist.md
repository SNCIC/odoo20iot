## P0 — 会造成真实数据丢失或 DDL 建表失败

### R-01 遥测 ACK 时机与 at-least-once 自相矛盾 ✅ 已修复

- **原位置**：`03-ingestion.md` §4.3（步骤 2 SETNX → 步骤 6 异步攒批 → 步骤 7 ACK）
- **问题**：先入异步 batcher 再 ACK，进程在 flush 前崩溃 → 消息已 ACK、数据未持久化 → **永久丢失**。
- **处置**：采用建议 **A** —— **ACK 移到持久化确认之后**。
  - `03-ingestion.md` §4.3：流程重写，步骤 7 改为「持久化确认后 → 写 done 标记 → 删 processing → ACK」；补充 `MaxAckPending ≥ 2 × batchSize` 的容量约束。
  - `01-architecture.md` §6.1：流程图同步，并加注「ACK 不是入队后，是落库后」。
  - `03-ingestion.md` §4.3：`Batcher.onFlush` 注释明确「必须返回持久化结果：nil 才算成功」。

### R-02 SETNX 幂等顺序会导致永久丢数据 ✅ 已修复

- **原位置**：`03-ingestion.md` §4.3 步骤 2
- **问题**：处理前 SETNX 占位，SETNX 后崩溃 → 重投被判定重复并 ACK → 永久丢失且无告警。
- **处置**：改为**两阶段标记**。
  - `processing`（TTL 60s，≥ AckWait×2）：**仅作并发互斥**，命中必须 **NAK 延迟重试，绝不 ACK**。
  - `done`（TTL 5min）：**只在持久化后写入**；只有 `done` 命中才允许提前 ACK。
  - `04-rules-alarm-automation.md` §3.1「冷却」同步修正：`cooldown_s` 也必须两阶段（`processing` TTL = 整体超时，成功后才写 `done` TTL = cooldown），否则崩溃后会永久抑制场景。

### R-03「单设备严格有序」在 NATS JetStream 上不成立 ✅ 已修复

- **原位置**：`03-ingestion.md` §4.2（推荐消费端本地 `hash(device_id) % N`）
- **问题**：queue group 多副本下同一设备消息被随机投给不同实例，本地 sharding 保不住跨实例顺序。
- **处置**：采用建议 **A** —— **发布端分片 + 静态分片分配**。
  - `03-ingestion.md` §4.2 整节重写：`iot.telemetry.{project}.shard.{0..N-1}`；**每分片一个 durable consumer**，分片与实例**静态绑定**；实例故障时该分片**暂停消费**（不并行）以保证顺序；`N` 一经确定不再变更。
  - 新增「**哪一层真正需要顺序**」表，明确**顺序是为规则 `prev` 与影子合并服务的，不是为存储服务的**（GreptimeDB 按时序存储、幂等按 `ts+seq` 去重，均与到达顺序无关）。
  - `01-architecture.md` §6.1 / §7.1：subject 与流程同步改为分片形式。

### R-04 分区表唯一约束写法在 PostgreSQL 下建表即报错 ✅ 已修复

- **原位置**：`02-domain-and-data.md` §3.3（`t_device` / `t_command`）、`07-odoo-integration.md` §5.2（`t_integration_log`）
- **问题**：① PG 分区表的 `UNIQUE` 必须包含分区键，`UNIQUE(device_key)` **建表即报错**；② 分区表上的唯一索引只保证**分区内唯一**，不是业务幂等键的全局唯一。
- **处置**：
  - `t_device`：改为 `UNIQUE (project_id, device_key)`，并加行内注释说明原因。
  - **新增非分区表 `t_idem_registry(project_id, scope, idem_key, request_hash, state, ref_id, expires_at)`**，统一承担跨分区的全局幂等约束；由定时任务按 `expires_at` 清理（TTL 分档见 07 §4.3.1）。
  - `t_command` / `t_integration_log` 上的唯一索引**降级为普通索引**，两表只承担记录与查询职责。
  - `02` §3.4 新增「**PG 分区表的唯一约束限制**」专表，写明三条规则与违反后果。
  - `01` §6.2 步骤 1 同步改为「写 `t_idem_registry(scope='command')` + `t_command`」。

### R-05 设备级 HMAC 认证在数学上不可验证 ✅ 已修复

- **原位置**：`03-ingestion.md` §2.1（B 档 `password=HMAC-SHA256(device_key, secret)`）
- **问题**：服务端只存 `Argon2id(secret)`，Argon2 单向 → **无法重算 HMAC**，流程不可实现。
- **处置**：采用建议 **A** —— **B 档改为客户端直接提交 secret 原文**，服务端 Argon2id 校验。
  - 安全性依据写入文档：① secret 是 32 字节高熵随机串，非人类密码；② TLS 1.3 保护传输；③ `clientID == username == device_key` 强校验阻止跨设备冒用。
  - 抗重放需求的出口：走 C 档（mTLS），或启用 nonce challenge-response 变体 —— 后者需服务端以**可解密方式**保存 secret，已在凭据存储表中新增「Challenge 密钥（Vault AES-256-GCM）」一行。

### W-02 04 的 `prev.*` 语义全文未定义 ✅ 已修复

- **原问题**：变量表列了 `prev.*`、场景条件依赖它判断趋势，但「到达序还是 `ts` 序」「`seq` 回绕 / 乱序时如何取值」全未定义 → **规则引擎无法编码**。
- **处置**：`04-rules-alarm-automation.md` §1.2 新增专节 **「`prev` 的取值语义」**，逐维度定义：
  - **排序依据**：按 `ts`（设备上报时间）排序，**不按到达序** —— 理由写明「分片消费下仍可能因 NAK 重投而乱序到达，按到达序取值会让规则结果不可复现」
  - **取值来源**：**已落库的最后一条**，不含当前消息
  - **同 `ts` 重复**：取 `seq` 最大者；`seq` 相同取 `ingested_at` 最晚者
  - **`seq` 回绕**：**不作为跨 `ts` 的排序依据**，仅用于幂等去重与**同一 `ts` 内的并列裁决**（后者为四轮修正，见下方后注）
  - **乱序到达**（新消息 `ts` < 已落库最新 `ts`）：取「按 `ts` 排序时位于当前消息**之前**的那条」，**不是最新一条** —— 这是语义关键
  - **首条消息**：`prev = null`，表达式必须能处理 `null`
  - **跨重启 / 跨分片迁移**：从持久化数据重建，不依赖内存
  - 附**表达式写法约束**（✅ 允许 / ❌ 禁止各举例），禁止未处理 `null` 的写法
  - 附**性能约束**：读 Redis 最新值缓存 → 未命中回落 GreptimeDB 单点查询；缺失时 `prev = null`，**不得阻塞或重试**
  - ⚠️ **后注（四轮修正 F-02）**：本项当时把回落 SQL 写成 `ORDER BY ts DESC LIMIT 1`，**与「乱序到达」维度互斥** —— 对迟到消息取到的是**最新一条**（时间上的后一条），不是前一条。语义维度定对了，实现却反着写。已修正为 `(ts, seq) < (cur_ts, cur_seq) ORDER BY ts DESC, seq DESC LIMIT 1`（见 [四轮章](#四轮实现可写性回归处置版)）。

## F-01 · `05` 的 STRIDE 表与 §2.3 的默认档相反 ✅ 已修复

- **原位置**：`05-security.md` L9（STRIDE 表 Spoofing 行）vs §2.3（设备认证强化措施）
- **问题**：§2.3 已经按 03 的决策反转改为「**生产默认为 B 档设备级**」，并留下「口径同步记录」声明两份文档**逐字一致**；但同一文件的 STRIDE 表对策列仍写「三档设备认证（**项目级默认** / 设备级 / mTLS）」。**实现认证的人看到两处相反的「默认」，无法下手**；更糟的是这句声明被同文件的另一处文字直接证伪。
- **根因**：§2.3 **重复罗列了 03 §2.1 的档位表**，等于建立了第二个真相源。首轮修 R-15 时只扫了「设备认证」章节，没扫引用它的其他章节。
- **处置**：
  - `05` L9 STRIDE 表 → 「**设备级默认** / 项目级显式开启 / mTLS」。
  - `05` §2.3 顶部改为 **「权威定义在 [03 §2.1]，本节只是安全视角摘要；凡不一致一律以 03 为准」**，并保留表格作为安全评审视图。
  - `05` §3.3 同样标注 03 §2.2 为权威源（合并 F-05）。
  - 「口径同步记录」改写：**承认这是第 4 处漏网 + 写明根因是「第二真相源」** —— 比单纯声明「已一致」有用，因为它解释了为什么会漏。
- **教训（写入持续项）**：**凡是「摘要表 + 权威表」并存的章节，必须显式标注权威源**，否则修正必然漂移。已加入评审清单的持续检查项。

## F-02 · `prev` 的乱序语义与回落 SQL 互斥 ✅ 已修复

- **原位置**：`04-rules-alarm-automation.md` §1.2「`prev` 的取值语义」
- **问题**：九维度**字面齐全**，维度 5 明确要求乱序时取「按 `ts` 排序位于当前消息**之前**的那条」；但性能约束写的回落查询是 `ORDER BY ts DESC LIMIT 1` —— 对迟到消息（`ts` < 最新值）查出的其实是**最新一条**，即时间上的**后一条**。**语义与实现方向相反，规则引擎按文档写不出维度 5 的行为。**
- **处置**：采纳修复写法，并拆成「快路径 / 慢路径」说清 Redis 的边界：
  - **快路径**（`msg.ts` ≥ 缓存 `_ts`，即非迟到）：读 Redis 最新值缓存，零额外查询。
  - **慢路径**（迟到 / 缓存未命中）：回落 GreptimeDB，查询改为

    ```sql
    WHERE project_id = $1 AND device_id = $2
      AND (ts, seq) < ($3, $4)          -- 行值比较：严格早于当前消息
    ORDER BY ts DESC, seq DESC
    LIMIT 1;
    ```

  - 明确 **迟到消息不更新 `cache:...:last`**，所以「迟到必然走慢路径」是**预期行为而非缺陷**（否则实现者会去"优化"成错的）。
  - 补 **`seq` 缺失的兼容处理**：退化为 `ts < $3 ORDER BY ts DESC LIMIT 1`，并计数 `prev_tiebreak_degraded_total`，用于判断是否值得在 SDK 契约里强制上报 `seq`。
- **顺带修正一处措辞**：维度 6「`seq` 回绕」原文写「`seq` **不参与** `prev` 判定」，与维度 3「同 `ts` 重复取 `seq` 最大者」**字面互斥**。已改为「**不作为跨 `ts` 的排序依据**，仅用于幂等去重与**同一 `ts` 内的并列裁决**」—— 保留了原意（`seq` 不能当全局序），同时消除了与维度 3 的矛盾。

## F-03 · 可选 HMAC 变体缺「可解密存储」前提 ✅ 已修复

- **原位置**：`05-security.md` §2.3 通用要求表「HMAC 挑战（可选）」行
- **问题**：该行让 `password = HMAC(secret, server_nonce)`，但**默认 B 档只存 `Argon2id(secret)`** —— 单向哈希无法重算 HMAC。**这正是首轮 R-05 已修复的缺陷，在「可选路径」里复活了**（默认路径不受影响，所以更隐蔽）。
- **处置**：该行补上前提 —— **服务端必须能以可解密方式保存 secret**（Vault / KMS，AES-256-GCM，对应 03 §2.1「Challenge 密钥（可选变体）」行），并写明**启用即等于放弃「凭据不可明文存储」红线，需显式评估后按租户开启**。
- **说明**：`03` §2.1 的勘误记录里其实已有这个前提，缺的是 `05` 这一侧的对齐 —— 属 F-01 同一类「摘要没跟上权威源」的问题。

## F-04 · 幂等账本归属术语矛盾 ✅ 已修复

- **原位置**：`07-odoo-integration.md` §5.2.1（「账本在 Odoo，**IoT 侧不建第二本账**」）vs `08` §2.1 / `02` §3.3（「账本在 PG `t_idem_registry`」）；`07` §4.3.1 自称写的是后者。
- **问题**：**同一件事在文档里有两种互斥表述**，实现者无法确定 IoT 侧到底该不该建幂等表。
- **裁定**：**两本账都存在，且不是冗余 —— 按 `scope` 划分，作用域不重叠。** 07 §5.2.1 的原话只在「IoT → Odoo 写回」这一条路径上成立，被当成全局结论后就越界了。

  | 幂等范围 | `scope` | 权威账本 | PG / Redis 角色 |
  |---|---|---|---|
  | 命令下发、内部事件、告警通知 | `command` / `event` / `alarm_notify` | **PG `t_idem_registry`** | PG 即账本 |
  | IoT → Odoo 写回 | `integration` | **Odoo `edge_idempotency`** | PG 存本地回执（非权威）；Redis 仅加速 |

  裁决依据：**Odoo 写回路径**的业务写与幂等记录在 Odoo **同一事务**提交（07 §4.3.1），IoT 侧无法独立判断业务是否生效，只能做回执；而**命令下发这类不落 Odoo 的操作，Odoo 根本无从裁决**，只能由 PG 承担（这也是 `t_idem_registry` 必须独立成非分区表的直接原因）。
- **处置**：重写 07 §5.2.1（含勘误说明与上表 + 判定顺序）；07 §4.3.1 摘要行、08 §9 决策 2、README **ADR-015** 同步改为「唯一约束为账本，**按 `scope` 划分**」。共同红线不变：**Redis 从不是账本**。

## 附录 F：本轮派生的持续检查项

四轮暴露的共同模式是 **「摘要与权威源并存 → 摘要必然漂移」**。据此新增三条持续检查项（已并入 06 §7 持续项）：

| # | 检查项 | 频次 |
|---|---|---|
| 1 | **「权威源标注」检查**：凡文档中出现「重复罗列另一文档的表格/定义」的章节，必须显式标注权威源，否则视为缺陷 | 每次修订 |
| 2 | **「语义 → SQL/代码」反查**：凡正文给出语义定义（如「取前一条」）且随后给出查询/伪码的段落，必须逐句核对两者方向是否一致 | 每次修订 |
| 3 | **「已修过一轮的位置」重点复查**：上一轮的修正点本身所在的文件与相邻章节，是本轮高发区（F-01 / F-03 均属此类） | 每轮评审 |

> **F-02 的教训值得单列**：语义维度**定得完整**（九个维度字面齐全），不代表**可执行**。定完语义必须再问一句「**照着这句，SQL 怎么写**」，并把它写下来 —— 本轮两个 P0 都是这样被抓出来的。
