## 二、设计输入与约束

### 2.1 业务目标

1. **设备统一接入**：屏蔽设备品牌、协议、报文差异，设备侧不改固件即可上云。
2. **数据管道与规则**：从采集到存储到告警到联动的闭环，规则可在线变更、无需发版。
3. **多租户 SaaS**：单集群服务多个租户/项目，租户间数据与资源强隔离。
4. **开放能力**：REST + MQTT 双通道开放 API，支持第三方系统与自有 App 集成。
5. **可私有化**：同一套代码支持公有云多租户与客户单租户私有化部署。

### 2.2 约束条件

| 类别 | 约束 |
|---|---|
| 团队 | Go 为主力语言，无 Erlang/Java 深度维护能力 |
| 运维 | 目标客户含私有化场景，中间件组件数量需可控（不引入 Kafka+Flink+Pulsar 全家桶） |
| 设备侧 | 含 ESP32/STM32 级别 MCU，RAM ≤ 64KB，不可依赖 X.509 证书 |
| 合规 | 需对标等保 2.0 三级，支持数据分区域存放 |
| 成本 | 单位设备月度基础设施成本需可控，避免过早引入重型组件 |

### 2.3 明确不做（Out of Scope，一期）

- 自研 MQTT Broker 协议内核的完全重写（在成熟库上做增强）
- 通用流式 SQL 计算引擎（一期用自研窗口算子，不引入 eKuiper；出现复杂聚合需求时再评估）
- 任意 JavaScript 作为规则引擎地基（只保留受限「逃生舱」用于复杂转换，见 ADR-003）
- 自建机房 / 裸金属编排（统一以 Kubernetes 为交付面）
- 多地域双活（一期主备，双活列入 Phase 4 之后的评估项）

## 三、非功能性需求（NFR / SLO）

### 3.1 可用性与可靠性

| 维度 | 目标 | 验证方式 |
|---|---|---|
| 数据面可用性 | 99.95% / 月（停机 ≤ 21.6 min） | 黑盒探针 + SLO 面板 |
| 控制面可用性 | 99.9% / 月 | API 拨测 |
| 台账数据 RPO | 0（同步复制 + PITR） | 故障演练 |
| 遥测数据 RPO | ≤ 1 min（允许少量丢失） | 断网注入 |
| 时序数据 RTO | ≤ 15 min | 主备切换演练 |
| 控制面 RTO | ≤ 30 min | 跨 AZ 切换演练 |
| 消息投递语义 | 遥测 = at-least-once；命令 = at-least-once + 幂等；告警 = effectively-once | 幂等回归用例 |

### 3.2 容量与性能

| 指标 | 一期目标 | 扩展上限 | 说明 |
|---|---|---|---|
| 并发 MQTT 连接 | 100 万 | 1000 万 | 网关水平扩展 |
| 入站消息吞吐（峰值） | 50 万 msg/s | 200 万 msg/s | 持续 1h 不劣化 |
| 遥测写入 | 100 万 points/s | 500 万 points/s | GreptimeDB 集群 |
| 单租户设备数 | 50 万 | 不限（物理隔离可选） | |
| **接入确认延迟** P99 | < 100 ms | 网关收包 → 发布到 NATS（**不含持久化**） |
| **持久化延迟** P99 | < 500 ms | 消息持久化 → 可被查询（含攒批窗口） |
| 规则触发延迟 P99 | < 200 ms | 消息持久化 → 规则动作开始 |
| 遥测查询（单设备近 1h）P95 | < 300 ms | |
| REST 读 API P95 / P99 | < 200 ms / < 500 ms | |
| 指令下发（在线设备）P95 | < 1 s | 含跨节点路由 |
| 网关节点伸缩 | 3 min 内完成 ±50% | HPA + 自定义指标 |
| GC 停顿 | P99 < 10 ms | Go runtime 调优 |

### 3.3 安全与合规

见 [05-security.md](./05-security.md)。关键红线：

- 设备凭据**不可明文存储**，一律哈希 + 可轮换 + 可吊销。**生产默认设备级（`per_device`）**；项目级共享凭据（A 档）仅用于试用/PoC，需显式开启并接受风险声明（ADR-008）。
- 规则**条件判断**使用类型安全的表达式引擎（`expr`），不执行任意脚本；仅**复杂转换**允许受限沙箱脚本（L3 逃生舱，默认关闭），且禁止网络与文件 IO。
- 所有外部存储与中间件**一律通过网络协议访问**，禁止 cgo 链接其客户端库。**但这只降低「链接型衍生」争议，不等于完全规避** —— SaaS 提供、修改源码、私有化分发三种情形仍需逐项法务评估（ADR-010）。
- 所有敏感操作留**不可篡改审计日志**，留存 ≥ 180 天。
- 全链路 TLS，内部服务间 mTLS；支持国密套件（可选交付项）。

### 3.4 可观测性

| 类型 | 方案 | 留存 |
|---|---|---|
| Metrics | Prometheus / VictoriaMetrics + Grafana | 原始 15 天，降采样 1 年 |
| Logs | 结构化 JSON → Loki（或 ELK） | 30 天热，180 天冷 |
| Traces | OpenTelemetry → Tempo / Jaeger | 7 天（错误 100% 采样，正常 1%） |
| 告警 | Alertmanager → 飞书/钉钉/PagerDuty | |
| 审计 | PG 分区表 + 对象存储归档 | 180 天在线 + 3 年归档 |

## 五、架构决策记录（ADR 摘要）

| 编号 | 决策 | 结论 | 主要理由 | 备选与切换成本 |
|---|---|---|---|---|
| ADR-001 | MQTT Broker 形态 | **接入网关内嵌 mochi-mqtt 派生版 + NATS 集群总线** | 需做物模型级 ACL、限流、租户配额等深度定制；团队无 Erlang 栈 | EMQX 集群（对外协议一致，切换成本中等） |
| ADR-002 | 时序存储 | **GreptimeDB** | Apache-2.0，**无许可证传染风险**；云原生、写入性能与压缩比满足 IoT；同时支持 SQL 与 PromQL | 通过 `TimeSeriesStore` 接口抽象，可切 TDengine（须走 taosAdapter REST/WS）/ TimescaleDB |
| ADR-003 | 规则引擎形态 | **分层：`expr` 条件 DSL + 自研 DAG 编排 + 受限 JS 逃生舱（P2，默认关闭）** | 90% 规则只需条件判断，`expr` 类型安全、可静态分析、**无沙箱逃逸面**；把任意 JS 沙箱当地基是方向性错误 | 编排层若需成熟实现，可评估 RuleGo（Apache-2.0）替换自研 DAG |
| ADR-004 | 一致性模型 | **台账强一致 + 遥测最终一致 + 命令幂等** | 成本与可靠性的最优平衡 | — |
| ADR-005 | 多租户隔离 | **默认共享库 + `project_id` + PostgreSQL RLS** | 成本低、运维简单 | 大客户切独立 schema / 独立库 / 独立集群 |
| ADR-006 | 内部事件总线 | **NATS JetStream**（不引入 Kafka） | 组件少、Go 客户端成熟、支持持久化与 KV | 超大吞吐场景可增挂 Kafka 做旁路 |
| ADR-007 | 交付与部署 | **分层交付：Lite（Compose/单机 K3s，≤5 万设备）/ Standard（K8s + Helm + ArgoCD）/ Large（多 AZ HA）** | 早期只写「Kubernetes only」对中小私有化客户过重；分层后 Phase 1 可先用 Lite 跑通（评审 R-22） | 交付分层表见 [01 §5.3](./01-architecture.md)；**三层共用同一份代码 + 配置差异，禁止分叉精简版** |
| ADR-008 | 设备认证 | **三档：设备级（`per_device`，生产默认）/ 项目级（显式开启，仅试用 PoC）/ mTLS** | **决策反转**：早期默认项目级并要求强制 IP 白名单，但蜂窝/移动设备出口 IP 动态，该约束不可行。既然最强补偿措施落不了地，项目级就不能作生产默认 | A 档保留为「快速接入」；需二次确认风险声明，设备数 > 1000 时禁止开启 |
| ADR-009 | 服务间通信 | **HTTP/gRPC 用于同步查询，NATS 用于异步事件** | 明确边界，避免全异步带来的可调试性灾难 | — |
| ADR-010 | 外部依赖接入方式 | **一律通过网络协议访问，禁止 cgo 链接数据库/中间件客户端库** | 规避 GPL/AGPL「链接即衍生作品」风险，同时保证组件可替换 | 若未来必须 cgo，需法务出具意见 |
| ADR-011 | 与 Odoo 的集成通道 | **JSON-2 API（`/json/2`，Bearer API Key，必须带 `X-Odoo-Database`）拉取 + 自建 `sn_edge_integration` 模块写回 + 高价值事件走 Outbox、低价值走 `base.automation` webhook** | `/jsonrpc` `/xmlrpc` 已弃用（Odoo 22 移除）；写回的业务规则应归属 Odoo 侧；webhook 是 postcommit 异步但**非持久**，故高价值事件必须有 Outbox | 契约集中在 Go 侧 `pkg/odoo` 适配层，可局部替换为纯 JSON-2 标准方法 |
| ADR-012 | Odoo 数据访问边界 | **禁止 Go 直连 PostgreSQL 写；只读直连仅限离线分析** | 直连绕过 ORM/ACL/记录规则/审计/业务约束，且与 ORM 事务竞态 | 只读场景用独立只读账号 + 视图隔离；失败不影响在线链路 |
| ADR-013 | 与 `odoo-gateway` 的边界 | **人的流量只有一个入口（`odoo-gateway`），设备的流量只有一个入口（IoT 平台），两者仅在 `odoo-connector` 处单向交汇** | 两类流量差两个数量级（交互式 HTTP vs 百万长连接 + 50 万 msg/s），合并会互相绑架扩缩容 | 例外：IoT 运维控制台可直连 IoT API，但用户身份必须经 Odoo OIDC 联合，不得有独立账号体系 |
| ADR-014 | 桥接模块收敛 | **合并为单一模块 `sn_edge_integration`**（含 `edge_facade` / `iot_facade` / `edge_job` / `edge_idempotency` / `edge_outbox` + 5 个 `iot.*` 模型） | 两个模块会产生两套幂等表、两套 outbox、两套审计、两套服务账户映射 | **模块位置（五轮更正）**：放 `odoo20tbb/addons`（该目录是独立 git 仓 `SNCIC/odoo20tbb`）。原文写的「`myaddons` 规范」**已失效** —— 旧布局 2026-09-21 已删除。**manifest 按服务器约定**：`version = 20.0.x.y.z`、`author = SNCIC`、`license = LGPL-3`；模型名沿用 `edge_*`（对齐 PDF 契约）与 `iot_*`（本项目扩展） |
| ADR-015 | 幂等模型 | **五态状态机 + 数据库唯一约束为账本，账本按 `scope` 划分**：`ABSENT → PROCESSING → SUCCEEDED / FAILED_RETRYABLE / FAILED_FINAL`。**IoT→Odoo 写回** → Odoo `edge_idempotency`，`UNIQUE(company_id, integration_name, idempotency_key)`；**IoT 内部操作**（命令/事件/告警）→ PG `t_idem_registry`。Redis 仅加速 | Redis 会丢数据，不能作为唯一幂等账本；同键不同请求摘要必须拒绝。**两本账不是冗余**：主键不同、作用域不重叠，各有不可替代的裁决依据（详见 07 §5.2.1） | `expires_at` 按 `integration_name` 分档（交互 7 天 / 设备离线重传 30 天 / 人工补单 90 天） |
| ADR-016 | Rust 引入时机 | **一期不引入 Rust**；边缘先用 Go；Rust 只用于「已被 profiler 证明的 CPU 热点」，且优先独立进程、优先复用组织级基础设施 | 对齐《技术方案》p.13/p.37 的准入门槛；当前连 profiler 数据都还没有 | 候选热点：边缘二进制协议解析、压缩/加密；**时序降采样与规则匹配属 IO/并发型，不建议过早上 Rust** |
| ADR-017 | Odoo 扩展策略 | **允许在 `sn_edge_integration` 内 `_inherit` 扩展核心模型（新增 `iot_*` 字段）与新增 `iot.*` / `edge.*` 模型；禁止修改核心字段定义、禁止覆盖核心方法语义、禁止改上游源码树** | 早期「零改动」约束造成了多处设计扭曲（位置无处存、产量只能漂在 Odoo 之外、working_state 不可写导致状态无处落、Community 无质检）；放开后必须同步建立升级风险控制 | 全部改动集中在单一模块 + **扩展登记表** + 逐项升级影响评估；违反即阻断合并 |

## 六、与外部系统（Odoo 20）集成的关键结论

详见 [07-odoo-integration.md](./07-odoo-integration.md) 与 [08-odoo-perf-alignment.md](./08-odoo-perf-alignment.md)。六条必须记住的：

1. **Odoo 20 实例没有可用的 IoT 栈** —— `addons/iot_drivers` 被显式 `installable: False`，`iot_webserial` 仅浏览器 Web Serial。设备接入必须由本项目承担。
2. **Odoo 不进遥测热路径** —— 该实例单机、`workers = 0`（开发模式）、`max_cron_threads = 0`。集成一律「事件级、异步、可积压、最终一致」。**注意**：`max_cron_threads = 0` 会让 Outbox 投递在开发环境不执行，集成测试需临时调起（见 07 §2.6 第 10 项）。
3. **不修改上游源码与核心字段定义；允许受控扩展** —— 在 `sn_edge_integration` 单一模块内以 `iot_` 前缀新增字段与模型（ADR-017），映射权威仍在 IoT 平台的 `t_external_ref`。**扩展登记表（`EXTENSIONS.md`）为 CI 强制项**，保证 Odoo 升级（20→21/22）可控。
4. **本项目是《Odoo 20 高性能架构技术方案》在 IoT 垂类的实例化** —— 该方案的「设备厂商与工业物联网」章节（手册 p.35）已为本项目预留位置，两者的路线图应合并为一套。
5. **桥接模块只有一份** —— `sn_edge_integration`（ADR-014），同时服务 `odoo-gateway` 与本项目。合并是为了避免两套幂等表 / outbox / 审计。
6. **人的入口与设备的入口分离** —— 人的流量只走 `odoo-gateway`，设备的流量只走 IoT 平台，两者仅在 `odoo-connector` 处单向交汇（ADR-013）。
7. **允许扩展 Odoo，但需登记** —— 在 `sn_edge_integration` 内可新增 `iot_*` 字段与 `iot.*` 模型（ADR-017），用于承载位置、责任人、产量 staging、质检等原本无处可落的数据。**扩展登记表为 CI 强制项**，禁止修改核心字段定义、禁止覆盖核心方法语义、禁止改上游源码树（铁律 R4/R6）。
