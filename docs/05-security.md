# 05 · 安全设计

> 目标：对标等保 2.0 三级，支持数据分区域存放，满足私有化交付审计要求。

## 1. 威胁模型（STRIDE）

| 威胁 | 场景 | 对策 |
|---|---|---|
| **S**poofing 伪造身份 | 伪造设备上报、伪造应用调用 API | 三档设备认证（**设备级默认** / 项目级显式开启 / mTLS）、应用端 OIDC + JWT、请求签名 + nonce 防重放 |
| **T**ampering 篡改 | 篡改上报数据、篡改固件 | 传输 TLS、固件签名（Ed25519）、关键数据服务端时间戳打标 |
| **R**epudiation 抵赖 | 用户否认执行了删除操作 | append-only 审计日志（含 before/after、trace_id、IP） |
| **I**nformation Disclosure 信息泄露 | 跨租户越权读数据、日志泄露凭据 | PG RLS + 强制 `project_id` 过滤、Subject 携带租户、日志脱敏、字段加密 |
| **D**oS 拒绝服务 | 海量假连接、超大报文、规则死循环 | 连接速率限制、报文大小上限、令牌桶、沙箱超时与指令数限制、LB 层 DDoS 防护 |
| **E**levation of Privilege 提权 | 设备订阅他人 topic、普通用户执行管理员操作 | 物模型驱动 ACL（禁止通配符）、RBAC + 资源级鉴权、服务间 mTLS + SPIFFE 身份 |

**额外风险**：

| 风险 | 对策 |
|---|---|
| 规则脚本逃逸 | **默认不执行任何用户脚本**：条件判断用 `expr`（类型安全、无逃逸面），编排为受控 Go 动作注册表；仅 L3 逃生舱允许受限 JS（默认关闭、租户白名单、50ms 超时 / 内存 / 指令数限制 / AST 扫描） |
| SSRF（Webhook / OTA 下载） | 出站白名单 + DNS 固定解析 + 禁止内网段 + 统一出口代理 |
| 供应链投毒 | 依赖锁定 + `govulncheck` + Trivy + SBOM + 镜像签名 + 准入控制 |
| 密钥泄露 | Vault 动态凭据 + 短 TTL + 自动轮换 + 泄露检测 |
| 时序库跨租户串查 | 查询层强制注入 `project_id` 条件（不可由用户 SQL 覆盖） |

## 2. 身份与认证

### 2.1 身份类型

| 身份 | 凭据 | 生命周期 |
|---|---|---|
| 设备 | `device_key` + `secret`（32B 随机） | 长期，可轮换/吊销 |
| 应用（第三方/App） | OAuth2 Client Credentials → JWT | Access Token 1h，Refresh 30d |
| 用户 | 用户名密码 + MFA / SSO(OIDC) | Session 8h |
| 服务（内部） | mTLS 客户端证书 + SPIFFE ID | 24h 自动轮换 |

### 2.2 三级令牌体系

| 令牌 | 层级 | 用途 | 签发者 |
|---|---|---|---|
| **System Token** | 租户级 | 服务端集成、批量管理设备、创建子令牌 | 用户在控制台创建（可设 scope 与 IP 白名单） |
| **Device Token** | 设备级 | 设备自身上报与接收指令 | `svc-auth` 按需签发（可选短期模式） |
| **User Token** | 用户级 | 前端 App / 控制台访问，带 RBAC | OIDC / 登录接口 |

**JWT 规范**：

```
alg:       ES256（推荐）/ RS256
iss:       https://auth.<domain>
sub:       {actor_type}:{actor_id}
aud:       iot-api | iot-mqtt
exp/iat/nbf
jti:       唯一 ID（用于吊销列表）
scope:     ["device:read","device:write","telemetry:read",...]
tenant:    project_id（强制，无此声明一律拒绝）
ver:       密钥版本
```

- **吊销**：`jti` 黑名单存 Redis（TTL = exp）；密钥轮换用 `kid` + JWKS 端点，支持双密钥并存。
- **校验**：本地 JWKS 缓存（10 min）+ 吊销检查（Redis，缺失时**拒绝**而非放行，遵循 fail-closed）。

### 2.3 设备认证强化措施

**权威定义在 [03 §2.1 设备认证](./03-ingestion.md)，本节只是安全视角的摘要。凡两处不一致，一律以 03 为准。**

**生产默认为 B 档设备级**；A 档项目级为**显式开启**，仅用于试用 / PoC。

> ⚠️ **口径同步记录（第二轮）**：本节曾出现三处与 03 §2.1 决策反转（默认 A→B、IP 白名单由强制改可选、轮换 180→90 天）不一致的表述，当时已逐处修正并声明「逐字一致」。
>
> **但该声明在下一轮评审中被自身证伪**：本文档开头的 **STRIDE 表仍写「项目级默认」** —— 这是第 4 处漏网。
>
> **根因**：本节**重复罗列了 03 的档位表**，等于建立了第二个真相源，两份各自演进就必然漂移；而「逐字一致」这种靠人肉比对的承诺无法自证。
>
> **修正策略**：本节保留表格作为**安全评审视图**，但顶部显式声明 **03 为权威**；每次修订 03 §2.1 时必须同步复查本节（已加入评审清单的四轮检查项）。

| 措施 | A 项目级（**显式开启**） | **B 设备级（生产默认）** | C mTLS |
|---|---|---|---|
| clientID 强校验 | 校验设备归属该 Project | `clientID == username == device_key` | TLS 层 CN |
| 凭据粒度 | **租户级共享**（爆炸半径 = 全租户） | 单设备 | 单设备 |
| IP / 地域白名单 | **可选**（仅固定出口 IP 时建议启用） | 可选 | 可选 |
| 异常检测 | **建议启用**（不依赖 IP：异常地理分布 / 异常连接速率） | 建议 | 建议 |
| 强制轮换周期 | **90 天**（到期前 30 天提醒） | 按需 | 证书 24h 自动轮换 |
| 凭据存储 | `Argon2id(ProjectKey)` / `SHA-256(AccessToken)` | `Argon2id(secret)` | 由 CA 体系管理 |
| 失败锁定 | 单 ProjectKey 20 次/分 → 锁 10 min | 单 `device_key` 10 次/分 → 锁 5 min | 按 IP |
| 越权审计 | 按 ProjectKey 维度记录每次失败、轮换与越界尝试 | 按设备 | 按设备 |
| 一键吊销 | **支持**（租户级，应急用） | 支持 | 支持 CRL |
| 开启条件 | 控制台二次确认风险声明；**设备数 > 1000 时禁止开启** | 无需额外确认 | 需 CA 体系 |

**通用要求**：

| 措施 | 说明 |
|---|---|
| HMAC 挑战（可选） | 高安全场景改为 `password = HMAC(secret, server_nonce)`，服务端下发 nonce，防重放。**前提：服务端必须能以「可解密」方式保存 secret**（Vault / KMS，AES-256-GCM）—— 默认 B 档只存 `Argon2id(secret)`，**单向哈希无法重算 HMAC**，直接套用该变体会重现 R-05 的「数学上不可实现」缺陷。启用此变体**等于放弃「凭据不可明文存储」这条红线**，必须显式评估后按租户开启（见 [03 §2.1 凭据存储规则与勘误记录](./03-ingestion.md)） |
| 首次激活 | 设备用产品密钥换取独立凭据，激活接口限速 + 需设备指纹 |
| 登录失败处理 | 三维计数：`device_key` / `project` / `IP` 分别独立限流，任一超阈即锁 |
| 物理安全 | 建议设备侧安全存储（ATECC608 / ESP32 flash 加密）；平台不假设设备安全，故凭据可随时吊销 |
| **A 档风险声明** | A 档的爆炸半径是**整个租户**，只应出现在试用、PoC，或设备数极少且出口 IP 固定的场景。**上表 A 列的措施为「可选开启、非强制」**（与 03 §2.1「A 档的控制措施（可选开启，非强制）」一致）—— 因此 A 档的门槛**不是「逐项落地才可开放」，而是「限制适用范围」**：控制台二次确认风险声明 + **设备数 > 1000 时禁止开启** |

## 3. 授权

### 3.1 分层授权模型

```
L1 租户边界     project_id 必须匹配（平台强制，不可绕过）
L2 角色权限     RBAC（Casbin）：owner / admin / operator / viewer / device_operator
L3 资源权限     资源级 ACL：设备分组、设备类型、具体设备
L4 操作权限     按 API 的 scope 校验
L5 字段权限     敏感字段（secret、密钥）仅 owner 可见，且只读、不返回明文
```

### 3.2 预置角色

| 角色 | 权限 |
|---|---|
| `owner` | 全部，含令牌管理、成员管理、删除项目 |
| `admin` | 全部业务操作，不含项目删除与计费 |
| `operator` | 设备/规则/场景/OTA 读写，不可管理成员与令牌 |
| `device_operator` | 仅设备读写 + 指令下发（用于现场运维） |
| `viewer` | 只读 |
| `api` | 受 scope 限制的编程访问 |

**Odoo 侧扩展字段的权限约束**（ADR-017 引入）：

| 字段类别 | 服务账号（`group_iot_facade` / `group_iot_device`） | 人工角色（`group_iot_manager`） |
|---|---|---|
| `iot_device_key` / `iot_project_id` / `iot_online` / `iot_last_seen` / `iot_firmware_version` / `iot_state` / `iot_state_ts` | 读写（connector 单向回写） | 只读 |
| `iot_site_id` / `iot_employee_id` | **只读**（业务配置，非设备数据） | 读写 |
| `maintenance.request.iot_*`（告警上下文 5 项） | 建时写入，之后只读（**不可篡改告警证据**） | 只读 |
| `iot.meter.reading` / `iot.quality.check` | 创建与状态流转 | 只读 + 可执行「应用 / 拒绝」动作 |

**红线**：**服务账号不得修改任何人工维护的业务配置字段**（位置、责任人、计量点换算规则、质检规格）。这类变更必须有人工操作者与审计记录。

### 3.3 身份归属与真相来源（评审 R-10）

平台有四类身份，早期文档只零散提到「svc-auth 管租户/用户/角色」，与 ADR-013「IoT 控制台用户身份必须经 Odoo OIDC 联合、不得有独立账号体系」表述冲突。现明确各自身份的**真相来源**：

| 身份类型 | 真相来源 | 认证方式 | 凭据存储 | 备注 |
|---|---|---|---|---|
| **Odoo 用户**（运维控制台、`maintenance` 操作、指令审批） | **Odoo**（`res.users`） | Odoo 会话 / OIDC | Odoo 负责 | IoT 控制台**不建独立账号**，登录走 Odoo OIDC 联合（ADR-013） |
| **IoT 项目成员**（业务角色、权限范围） | **`svc-auth`**（`t_user` / `t_user_project_role`） | 由 Odoo 身份映射而来（联合登录后由 `svc-auth` 授予项目内角色） | PG + JWT | 身份来自 Odoo，**角色与项目归属**来自 IoT 平台 |
| **设备身份** | **`svc-auth` / 设备凭据表** | MQTT CONNECT（三档，见 03 §2.1） | `t_device.secret_hash`（Argon2id） | 设备**不是** Odoo 用户，不可换取 Odoo 身份 |
| **第三方应用身份** | **`svc-auth`**（OAuth2 client_credentials） | JWT（`scope` 受限） | `t_api_token` | 用于开放 API / Webhook 调用方 |

**边界规则**：

1. **身份来源与角色来源分离**：身份（你是谁）来自 Odoo；角色（你在本项目能做什么）来自 `svc-auth`。禁止在 IoT 侧另行维护一套密码。
2. **设备永不持有 Odoo 身份**：设备凭据只能访问设备域 API，`company` 由服务端映射链决定，不可由设备指定（07 §5.2.3）。
3. **第三方应用身份只走 `scope`**，与用户身份完全隔离；不得借用任何真实用户账号。

### 3.4 指令下发授权与审批（对应 Odoo 集成决策 #19）

设备指令是**双向安全边界**上风险最高的操作：它让一个 Odoo 用户能够物理影响现场设备。

**按风险分级**（物模型 `commands[].risk_level`）：

| 级别 | 示例 | Odoo 侧要求 |
|---|---|---|
| `low` | 查询状态、读取参数、时间同步 | 记录审计即可 |
| `medium` | 修改阈值、启停单个传感器 | `device_operator` 及以上角色；记审计 |
| `high` | 启停产线、固件升级、复位设备、修改安全参数 | ① `device_operator` 及以上；② **二次确认弹窗 + 填写理由**；③ 全量审计（含理由）；④ 可选 MFA 再验证 |

**分层校验（任何一层不得省略）**：

| 层 | 校验内容 |
|---|---|
| Go 网关 | 令牌有效、租户匹配、路由白名单 |
| IoT 平台 | 设备存在且属于该租户、指令在物模型 `commands` 白名单内、设备在线或可入离线队列、配额 |
| Odoo | 用户角色、公司范围、记录规则、`risk_level=high` 时的二次确认与理由 |
| 审计 | 主体（Odoo 用户）→ 意图（指令 + 参数 + 理由）→ 执行（`command_id`）→ 结果（设备应答）**全链路可追溯** |

**红线**：

1. **指令不接受匿名或纯设备凭据发起** —— 必须关联一个可追责的 Odoo 用户，或明确标记为系统自动（`actor_type='system'` + 关联规则 ID）。
2. **高危指令的二次确认不可由客户端实现** —— 前端弹窗可被绕过。必须在 Odoo 侧生成一次性 `confirm_token`，Go 侧校验通过后才转发。
3. 审计中**不得记录**可能含敏感参数的完整 Payload（如密码类参数），只记参数名与摘要哈希。

### 3.3 设备 ACL（物模型驱动）

**权威定义在 [03 §2.2 ACL（物模型驱动）](./03-ingestion.md)**，本节为安全视角摘要。核心规则：

- 设备只能发布到自己的命名空间。
- 设备订阅 **禁止通配符**（`#`、`+`），只允许精确 topic 或平台预定义的允许通配。
- 越权尝试写入安全事件（`t_audit_log.action='acl.deny'`），同一设备 1 分钟内 5 次越权 → 自动断开并降级。

## 4. 传输与存储加密

| 环节 | 方案 |
|---|---|
| 设备 ↔ 网关 | TLS 1.3（禁止 1.0/1.1）；密码套件白名单；支持 mTLS；可选国密 SM2/SM4（私有化交付） |
| Web/App ↔ API | TLS 1.3 + HSTS + 安全响应头（CSP、X-Frame-Options、X-Content-Type-Options） |
| 服务间 | mTLS（Istio/Linkerd 或 cert-manager + 自签 CA）；证书 24h 轮换 |
| 数据库 | PG：TLS + 静态加密（云盘加密 / LUKS）；GreptimeDB：TLS + 磁盘加密 |
| 对象存储 | SSE-S3 / SSE-KMS；敏感桶私有 + 预签名 URL（TTL ≤ 1h） |
| Redis | TLS + `requirepass`（ACL 用户隔离）；不使用公网暴露 |
| 备份 | 全量加密后落对象存储，密钥独立管理 |
| 敏感字段 | `secret_hash`（Argon2id）、第三方凭据（AES-256-GCM，密钥在 Vault）、手机号/邮箱（可按租户开启字段级加密） |

**禁止事项**：

- 禁止在日志、异常堆栈、审计中打印设备 secret、JWT、AK/SK（统一脱敏中间件 + 正则兜底）。
- 禁止明文存储任何可凭以认证的凭据。
- 禁止使用 MD5/SHA-1 做安全用途。

## 5. 密钥与凭据管理

```
Vault / 云 KMS
├── transit: firmware-signing-key (Ed25519)     固件签名，仅 OTA 服务可调用
├── transit: jwt-signing-key (ES256)            JWT 签发，kid 轮换
├── kv:      webhook-secrets / 三方 AK-SK        加密存储
├── pki:     internal-ca                        服务间 mTLS 证书签发
└── database: 动态凭据（TTL 24h）                各服务数据库账号
```

| 要求 | 说明 |
|---|---|
| 无硬编码密钥 | CI 中静态扫描（`gitleaks`），提交即阻断 |
| 密钥不入镜像 | 通过 Vault Agent / CSI Driver 注入内存或临时文件 |
| 自动轮换 | JWT 密钥 90 天、mTLS 证书 24h、数据库凭据 24h、设备 secret 按需 |
| 轮换不中断 | 双密钥并存窗口；JWKS 端点同时提供新旧公钥 |
| 访问审计 | Vault 审计日志接入统一审计流水 |
| 备份与恢复 | Vault 快照加密异地备份；恢复演练每半年一次 |
| 泄露响应 | 支持一键吊销全部 JWT / 全部设备凭据（按租户或全局），有演练预案 |

## 6. 应用安全

| 类别 | 措施 |
|---|---|
| 注入 | 全部 SQL 使用参数化（`pgx` prepared statement / `sqlc` 生成）；禁止字符串拼接 SQL；GreptimeDB 查询由查询构建器生成且**强制注入 `project_id` 条件**（见 02 文档 §4.3） |
| XSS | 前端 Vue 默认转义；富文本（模板）使用 DOMPurify；CSP 严格策略 |
| CSRF | 使用 SameSite=Strict Cookie + 自定义 Header 校验；纯 Token 场景天然免疫 |
| 越权 | 统一鉴权中间件：先校验 `project_id`，再做资源归属校验（禁止只按资源 ID 查询） |
| 反序列化 | 不使用 `gob`/Java 风格反序列化；JSON 解析限制深度（≤ 20）与体积（≤ 32 KB） |
| SSRF | 见 §1 对策；统一出站代理 `egress-proxy`，仅允许白名单 |
| 文件上传 | 类型白名单（固件 bin/hex、图片 png/jpg）、大小限制、病毒扫描（ClamAV）、随机文件名、不落 Web 根目录 |
| 重放攻击 | 应用 API 支持 `X-Request-Id` + `X-Timestamp` + 签名（HMAC），时间窗 ±5 min，`jti` 去重 |
| 限流 | 三层：LB（IP）、网关（租户/用户）、业务（接口级） |
| 依赖 | `go.sum` 锁定；每日 `govulncheck` + Trivy 扫描；CVE 高危 7 天内修复 |
| 沙箱 | 规则脚本、表达式解析全部在受限环境，禁止 `os/exec`、`unsafe`、反射暴露 |
| 前端 | 无 sourcemap 上线；依赖锁定；第三方脚本 SRI |

## 7. 审计与合规

### 7.1 审计范围（必须记录）

| 类别 | 事件 |
|---|---|
| 认证 | 登录成功/失败、Token 签发/刷新/吊销、设备认证失败、MFA 变更 |
| 授权 | 权限变更、角色分配、ACL 拒绝、越权尝试 |
| 数据 | 设备/设备类型/物模型 增删改、批量导入导出、时序数据导出、影子变更 |
| 配置 | 规则发布/回滚、告警规则变更、场景/任务变更、OTA 任务创建与暂停 |
| 凭据 | 密钥轮换、secret 重置、第三方凭据变更 |
| 系统 | 项目创建/删除、配额变更、集群变更（运维操作） |

### 7.2 审计实现要求

| 要求 | 实现 |
|---|---|
| append-only | `t_audit_log` 表对应用账号仅授 `INSERT`/`SELECT`，无 `UPDATE`/`DELETE` |
| **完整性（按租户分链）** | **不采用全局单链**。改为**按 `project_id` 分链**（每租户独立的 `prev_hash` 序列），或**批次 Merkle 根 + 归档签名**。见下方说明 |
| 不可丢失 | 审计写入失败时**阻断原操作**（仅限同步写路径的关键操作）；异步路径落本地磁盘队列并重试 |
| 留存 | 在线 180 天 + 对象存储 WORM（合规模式）3 年 |
| 查询 | 审计查询本身也记审计 |
| 导出 | 仅 owner 且需二次确认，导出行为记审计，下载链接短时效 |

> ⚠️ **为什么不能用全局单 `prev_hash` 链（评审 R-20）**：全局单链在**高并发写入下是串行瓶颈** —— 每条记录都要读上一条的哈希，必须串行化，与平台的写入吞吐目标直接冲突。更危险的是，它与「审计写入失败则阻断原操作」叠加后，**审计链故障会放大为业务故障**。
>
> 修正：
> - **按 `project_id` 分链**：租户内串行、租户间并行。单租户的写入速率远低于全局，串行化可接受；单租户故障不影响其他租户。
> - **按时间分区归档时用 Merkle 根**：每个归档批次（如每月）计算一个 Merkle 根，用 Vault 中的密钥签名后写入归档清单。校验粒度从「逐条链」变为「逐批次根」，既降低写入成本，又保留可验证性。
> - **阻断范围收窄**：只有「安全关键操作」（凭据变更、权限变更、数据导出）才允许因审计写失败而阻断；普通业务操作降级为「本地磁盘队列 + 重试 + 告警」。
>
> `06` 文档的「审计链式哈希校验通过」验收项已同步调整为**按租户/按批次**的校验粒度。

### 7.3 合规对标

| 要求 | 落地 |
|---|---|
| 等保 2.0 三级 | 身份鉴别（双因素）、访问控制、安全审计、入侵防范、数据完整性/保密性、备份恢复、剩余信息保护 |

## 8. 供应链与运行时安全
