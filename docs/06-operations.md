# 06 · 高可用、可观测、运维与演进

## 1. 高可用设计

### 1.1 组件级 HA 矩阵

| 组件 | 拓扑 | 故障检测 | 切换机制 | 影响 | 恢复时间 |
|---|---|---|---|---|---|
| `gw-mqtt` | 3+ 副本，跨 AZ 打散 | LB 健康检查（TCP + HTTP /healthz，2s 间隔 3 次失败） | LB 摘除 + 客户端重连 | 该节点连接断开，设备重连 | < 30 s |
| `gw-http` / `gw-coap` | 2+ 副本 | K8s readiness | 自动 | 无 | < 10 s |
| `svc-*`（无状态） | 2+ 副本 | K8s readiness | 自动 | 无（请求重试） | < 10 s |
| `svc-automation`（有状态） | 3 副本 + 分片 | 分片心跳（Redis） | 分片重分配（10s 未心跳则抢占） | 该分片任务延迟 | < 30 s |
| NATS JetStream | 3 或 5 节点 Raft | NATS 内置 | Raft 选举 | 短暂发布阻塞 | < 10 s |
| PostgreSQL | Patroni + etcd（自建）或云 RDS 多 AZ | Patroni 探活 | 自动主从切换（`sr_check`） | 写不可用 | < 60 s |
| Redis | Cluster 3 主 3 从 | Cluster 心跳 | 从节点提升 | 缓存部分失效，降级到 PG | < 30 s |
| GreptimeDB | 3 副本集群（`replication_factor = 3`） | 内置（Metasrv） | 副本自动接管 | 写入短暂重试 | < 60 s |
| MinIO | 4+ 节点纠删码 | 内置 | 在线修复 | 读写降级 | — |
| Kubernetes | 3 master（etcd 3 或 5 节点） | kubelet / etcd | 自动 | 控制面短暂不可用（不影响已运行 Pod） | < 60 s |
| Ingress / LB | 双活 + VRRP / 云 LB | 健康检查 | 自动 | 无 | < 10 s |
| Vault | 3 节点 Raft | 内置 | 自动 | 密钥读取短暂失败（有缓存） | < 30 s |

### 1.2 关键设计约束

| 约束 | 说明 |
|---|---|
| **跨 AZ 强制打散** | 所有服务使用 `topologySpreadConstraints`（`maxSkew: 1`, `whenUnsatisfiable: DoNotSchedule`），同服务副本必须分布在不同 AZ |
| **PDB 保护** | 每个服务配置 `PodDisruptionBudget`（`minAvailable: 51%`），防止滚动更新与节点维护同时带走过多副本 |
| **优雅退出** | 所有服务监听 `SIGTERM`，先摘流（readiness=false）→ 等待存量请求完成（≤ 30s）→ flush 缓冲 → 退出。网关需在退出前向设备发送 DISCONNECT（含原因码）触发设备主动重连 |
| **禁止单副本** | 生产环境所有无状态服务副本 ≥ 2（除明确标注的使用 Leader 单实例的调度器，其自身有分片兜底） |
| **依赖隔离** | 数据面不依赖控制面（网关凭据走本地缓存 + Redis，Redis 不可用时用本地 LRU 降级）；控制面故障不影响设备上报 |
| **超时与熔断** | 所有跨服务调用必须配置超时 + 熔断（`gobreaker`）+ 有限重试；禁止无限重试 |
| **启动自检** | 服务启动时校验内核参数、依赖连通性、密钥可用性，任一失败则**拒绝启动**（避免带病运行） |

### 1.3 故障域与隔离

```
故障域层次（由大到小）：
  Region > AZ > 节点池 > 节点 > Pod > 容器 > 租户 > 设备

隔离措施：
  跨 Region   : 主备（异步复制）
  跨 AZ       : 副本打散 + 本地优先路由
  节点池      : 网关/应用/数据三类节点池相互隔离，避免资源争抢
  节点        : 资源 requests/limits 强制、QoS Guaranteed（核心服务）
  Pod         : 内存上限 + GOMEMLIMIT，防 OOM 扩散
  租户        : 配额 + 并发池 + 限流，单租户异常不影响他人
  设备        : 单设备限流 + 连接数上限 + 自动封禁
```

## 2. 容灾与备份

### 2.1 灾备目标

| 场景 | RPO | RTO | 方案 |
|---|---|---|---|
| 单 Pod 故障 | 0 | < 30 s | K8s 自动重建 |
| 单节点故障 | 0 | < 60 s | 副本接管，PDB 保障 |
| 单 AZ 故障 | ≤ 1 min | < 5 min | 跨 AZ 副本接管；PG 主库切换至其他 AZ |
| Region 故障 | ≤ 5 min | ≤ 30 min | 主备切换（备集群热备 + 数据异步复制） |
| 数据误删 | ≤ 5 min | < 2 h | PG PITR；GreptimeDB 快照恢复 |
| 勒索/恶意删除 | ≤ 24 h | < 4 h | 对象存储 WORM 不可变备份（异地） |

### 2.2 备份策略

| 数据 | 方式 | 频率 | 保留 | 验证 |
|---|---|---|---|---|
| PostgreSQL | WAL 归档（PITR）+ 每日全量（`pg_basebackup`） | 连续 + 每日 | 全量 30 天，WAL 7 天 | 每周自动恢复到临时库并跑校验查询 |
| Redis | RDB + AOF（`everysec`） | 每小时 RDB | 7 天 | 每月恢复演练 |
| GreptimeDB | 导出/快照（对象存储后端快照 + 逻辑导出） | 每日增量 + 每周全量 | 全量 8 周 | 每月抽查恢复 |
| 对象存储 | 跨区复制 + 版本控制 + 部分桶 WORM | 实时 | 按策略 | 季度抽查 |
| NATS JetStream | 关键 Stream 落对象存储快照 | 每日 | 7 天 | 季度恢复演练 |
| Vault | Raft 快照 | 每日 + 变更后 | 30 天 | 每半年恢复演练 |
| 配置/密钥/Helm | Git（GitOps 仓库） | 每次变更 | 永久 | 天然可追溯 |

**必须做到的 3 件事**：

1. **备份不等于可恢复**：每次备份后自动执行恢复验证（`restore-verify` Job），失败则告警。
2. **备份加密**：备份文件加密后传输与存储，密钥与备份分离存放。
3. **恢复演练**：每季度一次全链路恢复演练（含 Region 级），形成报告并跟踪问题项闭环。

### 2.3 混沌工程

| 实验 | 工具 | 频率 | 通过标准 |
|---|---|---|---|
| Pod Kill（随机服务） | Chaos Mesh `PodChaos` | 每周（staging） | 无用户可见错误；K8s 30s 内恢复 |
| 网络分区（AZ 间） | `NetworkChaos` partition | 每月（staging） | 跨 AZ 副本接管；数据无丢失 |
| 网络延迟/丢包 | `NetworkChaos` delay/loss | 每月 | P99 劣化 < 2 倍，无级联失败 |
| 依赖故障（Redis/PG/GreptimeDB 停） | 手动 + `PodChaos` | 每月（staging） | 按降级清单表现，无雪崩 |
| 磁盘 IO 延迟/满 | `IOChaos` | 每季度 | 写入告警正确触发，服务不崩溃 |
| 时钟偏移 | `TimeChaos` | 每季度 | 时序数据打标正确，无逻辑错乱 |
| 资源压力（CPU/内存） | `StressChaos` | 每月 | 限流/降级生效，其他租户无影响 |
| MQTT 异常客户端 | 自研混沌客户端 | 每次发布 | 恶意/异常报文不导致网关崩溃 |

**红线**：混沌实验必须在 staging 先跑通，生产仅允许在低峰期进行，且需提前通告 + 一键停止开关。

## 3. 可观测性与 SLO

### 3.1 指标（Metrics）

| 域 | 关键指标 | 说明 |
|---|---|---|
| 接入 | `gw_connections_current`、`gw_connect_rate`、`gw_connect_fail_total{reason}`、`gw_auth_success_total`、`gw_acl_denied_total` | 连接数与认证健康度。⚠️ `gw_connect_fail_total{reason=overloaded}` **必须与凭据失败分开告警**：前者是容量问题，后者才可能是攻击（03 §2.1.1 ⑤） |
| 消息 | `gw_msgs_in_total`、`gw_msgs_out_total`、`gw_msgs_dropped_total{priority}`、`gw_msg_size_bytes` | 吞吐与丢弃 |
| 管道 | `pipeline_consume_lag`、`pipeline_process_duration_seconds`、`pipeline_batch_size`、`pipeline_dlq_total` | 滞后与批处理效率 |
| 规则 | `rule_match_duration_seconds`、`rule_exec_duration_seconds`、`rule_exec_error_total{type}`、`rule_timeout_total` | 沙箱健康度 |
| 告警 | `alarm_active_total{level}`、`alarm_transition_total{from,to}`、`alarm_notify_total{channel,result}` | 告警链路 |
| 命令 | `cmd_issued_total`、`cmd_ack_duration_seconds`、`cmd_timeout_total`、`cmd_offline_queued` | 下发质量 |
| 存储 | `tsdb_write_duration_seconds`、`tsdb_write_fail_total`、`pg_query_duration_seconds`、`redis_cmd_duration_seconds` | 存储健康 |
| API | `http_request_duration_seconds{route,code}`、`http_requests_total`、`openapi_qps{tenant}` | 接口质量 |
| 资源 | `container_cpu_usage`、`container_memory_working_set`、`go_gc_duration_seconds`、`go_goroutines` | 运行时 |
| 业务 | `devices_online_total{tenant}`、`telemetry_points_total{tenant}`、`quota_usage_ratio{metric}` | 业务视角 |

**标签规范**：必须包含 `service`、`instance`、`environment`、`region`、`az`。**禁止**把 `device_id`、`trace_id`、`user_id` 作为 Prometheus 标签（高基数灾难）；这类维度走日志/追踪。

### 3.2 日志（Logs）

- 统一结构化 JSON：`{"ts","level","service","instance","trace_id","span_id","tenant","msg","error",...}`。
- 分级：`debug`（仅 dev/staging 特定开关）、`info`（业务关键节点）、`warn`（可恢复异常）、`error`（需人工关注）。
- **采样**：高流量路径的 `info` 日志按 1% 采样；`warn/error` 全量。
- **脱敏**：统一脱敏器处理 `secret`、`token`、`password`、`Authorization`、手机号、邮箱；正则兜底。
- 单条日志 ≤ 8 KB，超长截断并标注（防止日志放大攻击）。
- 留存：30 天热（Loki），180 天冷（对象存储）。

### 3.3 追踪（Traces）

- 端到端 `trace_id` 贯穿：设备消息 → 网关 → NATS → 管道 → 规则 → 存储 / 命令 → Odoo。
- **概念区分（评审 R-18）**：`trace_id` 是 **W3C `trace-id`（32 位十六进制）**；**HTTP / NATS / MQTT Header 中传递的是完整的 `traceparent`**（格式 `00-<trace-id>-<parent-id>-<flags>`）。业务消息信封里只放 `trace_id`，不在消息体里塞 `traceparent`。
- 采样：默认 1%；`error` 与 `duration > 1s` **强制 100% 采样**（尾部采样由 OTel Collector 实现）。
- 关键 span：`mqtt.connect`、`auth.check`、`acl.check`、`pipeline.process`、`tsdb.write`、`rule.exec`、`cmd.dispatch`。
- 保留 7 天。

### 3.4 SLO 定义与错误预算

| SLO | 目标 | SLI | 窗口 | 错误预算 |
|---|---|---|---|---|
| 数据面可用性 | 99.95% | 成功连接+消息处理 比例 | 30 天滚动 | 21.6 min/月 |
| 遥测入站成功率 | 99.99% | 网关接收成功比例（不含设备侧） | 30 天 | 4.3 min/月 |
| 命令下发成功率 | 99.9%（在线设备） | `acked / (acked+timeout+failed)` | 30 天 | 43 min/月 |
| API 可用性 | 99.9% | 非 5xx 比例 | 30 天 | 43 min/月 |
| API 延迟 | 95% 请求 < 200 ms | histogram | 30 天 | 5% 超预算 |
| **接入确认延迟** | P99 < 100 ms | 网关收包 → 发布到 NATS | 30 天 | — |
| **持久化延迟** | P99 < 500 ms | 消息持久化 → 可被查询（含攒批窗口） | 30 天 | — |
| 规则触发延迟 | P99 < 200 ms | 消息持久化 → 规则动作开始 | 30 天 | — |

> **三个 SLI 必须分别度量**（评审 R-06）。早期把「消息到达网关 → 落库确认」写成一个 P99 < 100ms 的指标，但攒批窗口本身是 200ms —— 物理上不可能。接入确认与持久化是**异步解耦**的两段，混在一起既无法定位问题，也给出了错误承诺。

**错误预算策略**：

- 预算消耗 < 50%：正常迭代。
- 消耗 50%–100%：暂停非必要变更，优先稳定性修复。
- 预算耗尽：**冻结功能发布**，仅允许修复类变更，直到预算恢复。

### 3.5 告警分级与响应

| 级别 | 触发示例 | 通知 | 响应时限 |
|---|---|---|---|
| **P0** | 数据面整体不可用、数据泄露、跨租户越权 | 电话 + 短信 + IM，全员 | 立即（5 min 内响应） |
| **P1** | 单 AZ 故障、PG 主库切换、管道滞后 > 50 万、错误预算耗尽 | 电话 + IM | 15 min |
| **P2** | 单服务副本不足、DLQ 增长、磁盘 > 85%、GreptimeDB 写入失败率 > 1%、降采样任务连续失败 | IM | 1 h |
| **P3** | 单设备异常、单租户配额 90%、慢查询增多 | IM（低优先级） | 1 工作日 |

**告警质量要求**：每条告警必须有 runbook 链接；连续 3 次误报的告警必须下线或调整阈值；每周复盘告警噪音。

## 4. 发布与变更管理

### 4.1 CI/CD 流水线

```
Push → Lint(golangci-lint) → Unit Test(≥70% 覆盖，核心包 ≥85%)
     → 契约测试(Protobuf/OpenAPI 兼容性) → SAST(gosec) → 依赖扫描(govulncheck/Trivy)
     → Build → 镜像签名(cosign) → SBOM 生成
     → Deploy to dev → 集成测试 → 压测基准对比（性能回归门禁）
     → Deploy to staging → Chaos 冒烟 → 人工审批
     → Deploy to prod（金丝雀）→ 观察 → 全量
```

**性能回归门禁**：核心基准（网关吞吐、管道延迟、规则执行耗时）对比主干基线，劣化 > 10% 则阻断合并。

### 4.2 发布策略

| 服务类型 | 策略 | 说明 |
|---|---|---|
| 无状态服务（`svc-*`） | 金丝雀 + 滚动更新 | 5% → 25% → 50% → 100%，每阶段观察 10 min |
| 网关（`gw-mqtt`） | 滚动更新 + 优雅摘流 | `maxUnavailable: 10%`；更新前 readiness=false，等待存量连接自然迁移（**不主动断开**，最多等待 6h，超时则按 10% 分批强制断开） |
| 有状态服务 | Operator + 分片迁移 | `svc-automation` 分片逐个迁移 |
| 数据库变更 | 扩展-收缩模式（Expand/Contract） | 见下 |
| 中间件升级 | 独立窗口 + 备份先行 | PG/Redis/GreptimeDB 主版本升级需单独 RFC |

### 4.3 数据库变更（零停机）

必须遵循 **Expand → Migrate → Contract** 三步：

1. **Expand**：加新列/新表/新索引（可空或有默认值），不删不改。使用 `CREATE INDEX CONCURRENTLY`。
2. **Migrate**：代码双写/双读，回填历史数据（分批，限速）。
3. **Contract**：确认无旧代码引用后，再删除旧列。

**禁止**：

- 单次变更锁表超过 1s（大表 `ALTER` 必须用 `pg_repack` 或新建表切换）。
- 在同一发布中同时做 schema 变更与逻辑变更（无法安全回滚）。
- 无 `down` 迁移脚本的 schema 变更。
- 直接修改历史迁移文件。

### 4.4 回滚

| 变更类型 | 回滚方式 | 时限 |
|---|---|---|
| 服务代码 | 回滚到上一镜像（ArgoCD `rollback`） | < 5 min |
| 配置 | 回滚 ConfigMap/Feature Flag | < 2 min |
| 规则/物模型 | 版本回滚（保留 7 天历史版本） | < 1 min |
| Schema | 使用预先准备的逆迁移脚本（仅限 Expand 阶段变更可逆） | < 30 min |
| 固件 | OTA 回滚任务（分批） | 按批次 |

**Feature Flag**：所有高风险功能必须由 Feature Flag 控制，支持按租户/按比例灰度与一键关闭，Flag 生命周期 ≤ 3 个月（到期强制清理）。

## 5. 容量规划与成本

### 5.1 容量换算（示例：100 万设备）

| 项 | 假设 | 计算 | 结果 |
|---|---|---|---|
| 峰值连接 | 100 万设备，80% 在线 | 80 万连接 | 网关节点：8C16G × 10 台（按 8 万/节点） |
| 消息速率 | 30s 上报一次，峰值系数 3 | 80万/30×3 ≈ **8 万 msg/s** | 网关 × 12 台（按 8000 msg/s/节点留余量） |
| 时序写入 | 每消息 5 个指标，峰值 3 倍 | 8万 × 5 = **40 万 points/s** | GreptimeDB 3 副本 × 3 节点（8C32G + NVMe） |
| 存储增长 | 40 万 points/s × 86400 × 每点 16B 压缩后 | ≈ **550 GB/天**（压缩后 ~80 GB/天） | 30 天热数据 ≈ 2.4 TB |
| NATS | 峰值 2 倍余量 | 20 万 msg/s 容量 | NATS 3 节点（8C16G） |
| PostgreSQL | 100 万设备 + 月 1 亿 command/alarm | — | 16C64G + NVMe 1TB，1 主 2 从 |
| Redis | 80 万在线态 + 最新值 | 每设备 ~2 KB | 约 3 GB → 3 主 3 从（16G × 6） |

> 以上为量级估算，**必须用实测压测结果校正**。安全水位取实测能力的 60%。

**容量口径（采纳《Odoo 20 高性能架构技术方案》手册 p.40 的排队论思路）**：

「先测四个基线，而不是套固定公式」——禁止照抄通用 QPS 数字：

| 基线指标 | 测量位置 | 用途 |
|---|---|---|
| 网关单连接服务时间 | MQTT + 消息处理耗时分解 | 确定并发上限 |
| 管道单分区吞吐 | `svc-pipeline` 分区延迟 | 确定分区数 |
| 规则单次执行耗时 | `svc-rule` by rule_type | 确定 worker 数 |
| **Odoo 单请求服务时间** | Odoo HTTP + SQL 分解 | **确定 connector 的限流与合并窗口** |

**估算结构（非承诺值）**：

```
Odoo 写入量 ≈ 有效告警数 × (1 - 告警合并率) + 产量回流频率 × 在线设备数
connector 队列等待 ≈ 告警到达速率 - connector 可持续处理速率
     ↑ 该值长期为正 → 队列无限堆积，必须降级（只记 IoT 侧，延后补建工单）
```

**验收方法**（对齐手册 p.39）：固定数据集与业务混合比例逐级升压；**一旦 Odoo 队列、数据库连接、锁等待或 P99 出现拐点，connector 的允许并发必须低于该点并留出维护余量**。起始配置由压测决定，不是承诺值。

### 5.2 成本优化手段

| 手段 | 收益 |
|---|---|
| 物模型 `storage.ts=false` | 减少 30%–60% 时序写入 |
| `deadband` 死区过滤 | 减少 20%–50% 消息量 |
| 降采样物化（1m/1h） | 查询成本降低 10–100 倍 |
| 冷热分层 + 对象存储 | 存储成本降低 60%+ |
| 网关按消息量而非连接数扩容 | 避免为低流量连接过度配置 |
| 使用 VictoriaMetrics 替代 Prometheus 集群 | 监控成本降低 50%+ |
| 压缩（zstd）+ 列存 | 时序存储压缩比 10–20 倍 |
| 资源 requests 精细调优 | 集群整体利用率从 20% 提升至 50%+（需配合 PDB 与容量水位保护） |

### 5.3 单位经济性跟踪

每月跟踪：`总基础设施成本 / 活跃设备数`、`成本 / 百万消息`、`成本 / TB 存储`。设定目标并跟踪趋势，异常上升需归因。

## 7. 演进路线（双轨并行）

### 7.0 组织方式：产品轨 × 工程轨

对比两份路线（`docs/ThingsCloud 物联网平台分析与 Go 自研参考.html` 的 6 个月 3 阶段 vs 本文档的 12 个月 4 阶段）：二者**不是矛盾，而是两条正交的轴**。

| 轴 | 回答的问题 | 依据 |
|---|---|---|
| **产品轨** | 「能不能卖」—— 功能成熟度 | 调研报告的功能优先级（P0/P1/P2） |
| **工程轨** | 「能不能扛」—— 生产就绪度 | 本文档的高可用 / 安全 / 可观测要求 |

**核心决策：把生产就绪做成每个阶段的退出条件（DoD），而不是独立阶段。**

原因：多租户 RLS、计量埋点、可观测这三样，**后补是重构，不是增加**。调研报告「先定价模型再定技术架构」的方向完全正确，但执行力度要推到「第一天就有 `project_id` 全链路贯穿 + 网关计量埋点 + 配额限流」。

### Phase 0 · 技术验证（第 1 个月）

| 交付 | 验收标准 |
|---|---|
| 网关原型（内嵌 mochi-mqtt） | 单节点 5 万连接稳定运行 24h，无内存泄漏 |

| ✅ **GreptimeDB JSON 字段能力验证**（2026-10-01 通过） | JSON 类型写入吞吐与提取查询性能达标；不达标则确认切「宽表」方案（02 文档 §4.1）。**结论：写入达标 3.8×；唯一超线的查询形态宽表同样超线 → 维持 JSON 为默认**。实测数据、GreptimeDB 版本边界与未验证项见 [02 §4.1.1](./02-domain-and-data.md)，原始报告 [docs/reports/b1-tsdb-bench.md](./reports/b1-tsdb-bench.md) |
| ✅ **`expr` 条件引擎验证**（2026-10-01 通过） | 编译期类型校验可用；求值 P99 ≤ 2 µs。**结论：均达标，但校验不能靠 `expr.Env`（物模型键是小写动态键），改为自建 AST 校验器**。实测 P99 0.98~1.74 µs（余量 1.15~2.04×，生产机型需复测）；同时勘误 3 处文档写法、补上 1 个安全缺口（谓词语法绕过内置关闭）与 1 条未定义的运行时语义（缺失指标）。见 [04 §1.2.1](./04-rules-alarm-automation.md) |
| **幂等与 ACK 时序验证**（评审 R-01/R-02） | 用故障注入证明：在「解析后崩溃」「入批后未 flush 即崩溃」两种场景下，消息**均能从 NATS 重投并被正确落库**，无丢失、无重复入库 |
| **分片消费与顺序验证**（评审 R-03） | 同一 `device_id` 在 3 副本 × N 分片下，规则 `prev` 上下文与影子合并均无乱序；实例故障接管期间该分片**暂停消费**而非并行 |
| **离线 Stream 元数据规模压测**（评审 R-12） | 给出 100 万设备下 Stream/Consumer 元数据规模，以及分片数 N 的选型依据 |
| ✅ **Argon2 认证容量与重连风暴**（评审 R-24，2026-10-01 通过） | 60s 内 N 台设备并发重连，网关 CPU 不饱和；给出 `t/m/p` 参数与副本数结论。**结论：参数改为 `t=3, m=32MiB, p=2`；并发上限 8（按内存带宽定）；「60s 内 8 万设备」这条口径本身不可行（需 51 个节点），改为端侧重连抖动摊到 ≥30 分钟（1 个节点）**。另发现 L1 缓存命中率与认证容量无关（只省 µs 级目录查询）。见 [03 §2.1.1](./03-ingestion.md) 与 [03 §5.3.1](./03-ingestion.md) |
| **L3 逃生舱限制 PoC**（评审 R-17） | 验证 goja 能否精确计数指令与硬限制内存；**不能则降级为「超时 + 并发上限」近似限制并如实标注** |
| **私有化 Lite 交付验证**（评审 R-22） | Compose 单机包在 4C8G 上跑通端到端（接入 → 落库 → 规则 → 告警）；**单实例消费 32 分片**的并行度与资源占用达标 |
| ✅ **QoS1 PUBACK 时机验证**（开工前清单 P0-4，2026-10-01 通过） | 验证 `mochi-mqtt` 能在「等待 NATS PublishAck 后再回 PUBACK」的语义下工作（`OnPublish` 阻止自动 PUBACK + 显式触发）；**注入网关崩溃证明设备会重传**。**这是 ADR-001 的明确定制点，不成立则需自建 PUBLISH 处理路径或回退 EMQX**。结论与边界见 [03 §4.4.1](./03-ingestion.md) |

## 8. 主要风险与对策

| 风险 | 影响 | 概率 | 对策 |
|---|---|---|---|
| **自研 MQTT 网关集群不稳定** | 高（核心链路） | 中 | Phase 0 决策点 + 保留 EMQX 回退路径 + 协议层无感切换 + 关键场景混沌覆盖 |
| **`expr` 表达力不足，被迫大量使用 L3 逃生舱** | 中 | 中 | 监控 L3 规则占比，超过 10% 即触发评估；为高频场景补充 Go 原生动作（而非放开脚本）；备选 WASM 沙箱 |
| **L3 沙箱逃逸** | 高 | 低 | L3 默认全局关闭 + 租户白名单 + 人工审批；逃逸用例强制纳入发布门禁 |
| **GreptimeDB 生态与运维成熟度不足** | 中 | 中 | `TimeSeriesStore` 接口抽象，可切 TDengine（走 REST/WS）/ TimescaleDB；关键查询只用标准 SQL，不依赖专有语法 |
| **依赖许可证变更导致商业化受阻** | 高 | 低 | 每个依赖 `LICENSE` 快照入库 + CI 校验 + 变更即阻断构建；**AGPL/SSPL 组件需逐项法务评估并满足四条件**（独立服务 / 不改源码 / 不链接 / 不同进程）—— MinIO 即属此类，不是"不引入"（ADR-010，口径见 01 §4.1） |
| **多租户越权** | 极高（信任崩塌） | 低 | RLS + 强制 tenant 中间件 + 自动化越权用例 + 每次发布门禁 |
| **100 万连接成本超预期** | 中 | 中 | 容量按 60% 水位规划；成本单位经济性月度跟踪；按需调整节点池 |
| **团队经验不足（IoT 领域）** | 高 | 中 | Phase 0 验证期；引入外聘顾问；关键模块先做 PoC |
| **中间件组件过多导致运维负担** | 中 | 中 | 严格组件准入（新增中间件需 RFC）；优先复用已有组件 |
| **需求蔓延（对标 ThingsCloud 全功能）** | 高 | 高 | 明确 Out of Scope 清单；能力对标矩阵分级（P0/P1/P2/P3）；每阶段只做当前优先级 |
| **私有化交付环境差异** | 中 | 高 | 早期引入私有化验收环境；Helm + 离线包；启动自检 + 兼容性矩阵 |
| **数据合规（跨境）** | 高 | 中 | 按 Region 分集群；跨境策略可配置为禁止；数据删除能力与证明 |
